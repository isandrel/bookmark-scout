# Extension stored data

Every stored value is an entry in `STORAGE_ITEMS` (`apps/extension/src/lib/storage/registry.ts`), and every setting is a field in `src/lib/settings-schema.ts` with its default in `config/settings/<tab>.toml`. The rules (key names, areas, `{ v, data }`, `update` under Web Locks, cleanup of unlisted keys, settings stored as overrides) are in "Config" and "Storage" under "Shared building blocks" in `apps/extension/AGENTS.md` and in the registry's header. Read both first; this skill is the order of work and the traps.

## Add a stored item

1. **Choose the area and say why** in the registry entry: `sync` only for small values the user expects on every device (8,192 bytes per item, 102,400 in total, never credentials); `local` for this device, caches, logs, and anything naming bookmark ids (ids differ per device); `session` for state shared by open pages until the browser closes (the manager's clipboard and undo history store ids and re-read them on use, skipping deleted ones).
2. **Key:** `<domain>.<name>` in kebab-case, `v: 1`, and a `backup` policy: `include`, `exclude` (device-bound, rebuildable, short-lived), or `secret` (never synced, never in a file). A field-level exception goes in the backup code: AI services are `secret` for keys and headers, but `aiEndpoints` keeps each Base URL in the backup (PR #644).
3. **Define it once** with `defineStoredValue(STORAGE_ITEMS.x, { schema | parse, empty })` in the module that owns it, and read it in React with `useStoredValue`. The zod schema lives in that module, not in the registry: the registry must stay importable in Node with no WXT auto-imports (E2E specs import it to name keys), and some schemas pull in code the background must not load.
4. **Collections** (`defineStoredCollection`, one item per id plus an index): write an entry before the index lists it and remove it after the index drops it; restore writes entries first and removals last; read with one batched `getMany`; remove orphans only after a grace period (`orphan_grace_hours` in `config/ai/prompt-library.toml`), because sync can deliver an entry before its index.
5. **Parse lists entry by entry** (`parseValidList`, `parseValidRecord` in `src/lib/storage/parse.ts`) so one malformed entry is dropped alone instead of emptying the collection. A value built from several items is a `defineDerivedValue`.
6. **Change it with `update`**, never by `set`ting a copy from an earlier read: `update` holds a Web Lock per key across pages and the background and re-reads inside it.
7. **Backup:** a new `include` item needs a source in `BACKUP_ITEMS` (`src/services/backup.ts`; `tests/unit/backup.test.ts` fails otherwise). Never key exported data by a field that is not unique: URL-keyed tags merged two bookmarks of one URL (PR #644). An IndexedDB database is not a stored item: one the backup holds (`backup: 'include'` in `INDEXED_DATABASES`, so far only covers) gets its own section and code, keyed by what is the same on another computer (covers by address, `cover-backup.lazy.ts`, loaded on first use so Settings does not grow), with each entry checked on restore and a review before anything is written.
8. **Disclose it** with the `privacy-disclosure-sync` skill: new synced or session items, and anything the backup or JSON export now holds, belong in `store/privacy-disclosures.md` and the policy (PRs #620, #622, #647).
9. **A new folder under `src/lib`** is not auto-imported: `imports.dirs` in `wxt.config.ts` lists `lib` and `lib/storage` separately. Add the folder there.

## Add a setting

1. Field in `settings-schema.ts`, default and bounds in the `config/settings/<tab>.toml` table of the Options section that shows it (`tests/unit/settings-config.test.ts` checks the placement).
2. **Size limits on every synced field** (`max_length`, `max_items`): `tests/unit/settings-storage.test.ts` fills every field to its largest with `<` (which Chrome stores as 6 bytes) and checks the settings item and each list's item against `SYNC_QUOTA.bytesPerItem` (`registry.ts`), and every synced item together (prompts at `max_prompts`, About me, the table view) against the total and the item count, with a margin: list settings (any setting whose default is a list, scope `lists` in `getSettingScope`) each have their own item, `sync:settings.list/<setting>` (a collection read and written as one `StoredRecord`, so a change writes only the lists that changed), and the rest share `sync:settings`. One shared lists item filled up at 8,022 of 8,192 bytes and pushed new lists onto the device (2026-10-23). Settings an earlier release kept elsewhere (lists in `settings`, one shared lists item, menus once per device) are moved by the `2026-10-sync-list-shards` migration (see "Migrations" below). Restrict list entries to one-byte printable characters where you can, or the limit you can offer collapses. Free text that would not fit at its worst case gets its own synced item instead of a settings field: About me (`sync:ai.about-me`, 1,000 characters) would have left room for about 75 characters inside `settings` (PR #699).
3. **Device-only settings** go in `DEVICE_SETTING_KEYS` (`registry.ts`), which stores them in `local:settings`; do not give one its own `local:` item. `changeSettings` writes only keys whose value changed, taking the sync, lists, and device locks in that order, so keys a newer release wrote survive.
4. **The total sync budget** is tested in `tests/unit/settings-storage.test.ts` ("sync quota"): every synced item at its largest, plus the prompts at their budget, must leave the stated margin under 102,400 bytes and 512 items. A new synced item fails until it has a size there; a new list setting is counted on its own. When the total does not fit, the message names the biggest items: lower their limits, `max_prompts`, or `prompt_max_bytes` in the same PR.
5. **Consumers:** map the setting to its consumer and test titles in `tests/settings-matrix.ts`, flip it in a test and assert the behavior changes, and make it apply live (see "Settings UX" in `extension-ui-change`).
6. **Removing a setting** touches the schema, the TOML, locale keys, the settings matrix, E2E seeds, and the docs settings pages in every language; a stale "AI Provider/AI Model" row survived one PR that way (PRs #614, #620).

## Turn a fixed behavior into a setting

The maintainer reviews for "configurable, extensible, customizable, maintainable" (root `AGENTS.md`) and often asks for a sweep ("what else can be configurable: the default view, the column order, the right-click menu and its order"). For each candidate:

1. **Setting, config, or code.** A value users will reasonably want different becomes a setting with today's behavior as its default. A value that guards a browser or provider limit stays in an app config file and becomes the setting's floor, checked by a test: Chrome allows two `captureVisibleTab` calls a second, so `browser_min_interval_ms` in `config/bookmarks/browse-covers.toml` bounds the user's Time Between Pictures (`tests/unit/browse-covers.test.ts`), at the maintainer's request. Only protocol constants stay in code.
2. **Shape.** Choices are enum ids, never display text; an order or a fallback chain (cover sources, menu actions, columns) is a list of ids the user can reorder, with the current order as the default; on/off groups go in a checklist (a list of fixed ids is `choiceListField`, drawn by `ChoiceListEditor`; an ordered list with hidden items is `OrderedChoicesList` in a panel, and an empty default can mean "every item in the config file's order" so items added later still show). Defaults and bounds go in the `config/settings/<tab>.toml` table of the Options section that shows it, with a comment saying what it does and why the default (`{ default, min, max, step, integer }` for numbers, `max_items` and `max_length` for lists).
3. **Field and placement.** Add it to `settings-schema.ts` in that section's `category(...)`; technical values most people never change go in the section's `advanced` list (the closed "Advanced settings" fold). Labels are `settings_<stem>`, `settings_<stem>Desc`, and optionally `settings_<stem>Help`, in every locale.
4. **Read it live** where the fixed value was read, and follow "Add a setting" above (size limits, device scope, the settings matrix, a test that flips it).
5. **Docs** name the setting in the settings page of every language with `<SettingDefault path="..." />`, never a typed default (`scripts/setting-defaults-docs.test.ts`), and the guide for the feature says it can be changed.

## Traps

- **Saving from a closing page.** A save started while Options unloads never gets through the lock; Options hands its last edit to the background (`'settings/save'` in `settings-storage.ts`). In E2E, wait until the value is stored before reloading.
- **Drafts across tabs.** A field holding a local draft must not write an unchanged draft back on blur: the Base UI NumberField overwrote another tab's newer value (PR #643, `tests/e2e/options-safety.spec.ts`). Test two Options tabs once per new field type.
- **Flash on open.** A component that depends on a stored value renders nothing until `useStoredValue(...).isLoading` is false (dismissed notices, PR #618).
- **Dismissed notices** are ids in `local:ui.dismissed-notices` (`backup: 'exclude'`): a new dismissible notice is a new id, not a setting.
- **Lock tests in Node.** CI's Node had no `navigator.locks`, so a two-instance unit test silently fell back to per-page queues and failed only in CI. Stub one shared lock manager (`tests/unit/stored-value.test.ts`).
- **Test helpers only.** Seed and read through `tests/e2e/storage.ts` (`setSettings`, `readSettings`, `writeStored`, `readStored`, `seedAIServices`) or `tests/unit/storage-helpers.ts`. `readSettings` returns overrides, so a setting back at its default reads as `undefined`.
- **Raising `v`** needs a migration step in `defineStoredValue`; a unit test fails without one. A newer `v` than the release knows is read but never written.

## Migrations

When a value must move to another item or shape that users of a store release have (a scope change, a split item), add a migration instead of dropping it; for one item's own shape, a `v` step in its `defineStoredValue` is enough. Migrations live in `src/lib/storage/migrations/` (the rules are in its `index.ts`):

1. **Add:** one module, `<yyyy-mm>-<name>.ts`, owning everything old: the old item (a `StorageItem` defined there, not in `STORAGE_ITEMS`) and a `recover(layers, legacy)` that returns the values found in old places by setting key and the keys to drop from this device. Register it in `MIGRATIONS` with `id` (the file name), `description`, `addedIn` (the package version now), and `removeAfter` (a later version; keep at least three releases and until the store dashboards show no installs from before it). Tests go in `tests/unit/migrations/<id>.test.ts`, an end-to-end check in `tests/e2e/migration-<id>.spec.ts`.
2. **What the runner does** (`runStorageMigrations` in `settings-storage.ts`, at every background start, after install or update, and when sync delivers settings or the old item): fills each found value into its scope only where nothing is stored there yet and only if valid, the list items in one `storage.sync.set` (120 writes a minute, 1,800 an hour), and records the id in `local:storage.migrations` once it found something; a failed write is logged and retried at the next start. Until then settings read through the migration, so nothing looks reset. The old item is never written or removed while the migration is registered: devices still on the earlier release read it, and the install cleanup keeps it (`isMigrationLegacyKey`). Old keys inside a current item (0.3.4's lists in `settings`) stay untouched while the migration's `keepsInSettingsItem` claims them; if the settings item would not fit the per-item quota with them, the writer saves it once more without them and logs it. The backup restore converts older files through the same `recover` (`upgradeBackupItems`).
3. **Remove:** `tests/unit/migrations/index.test.ts` fails once the package version reaches `removeAfter` (a version, not a date, so it fails in the release change and never on its own). Delete the module, its `MIGRATIONS` line, and its tests; nothing else. The cleanup then removes the old item on the next update, and the next settings save drops the old keys the migration kept in the settings item (`tests/unit/settings-stray-lists.test.ts`). No other file in `src` may name the old item (the same test checks).
4. **Why not WXT's migrations:** `storage.defineItem` versions run per item and on update only, and cannot move a value to another item; the registry here is the one mechanism.

## Dropping old data

Older releases' keys are removed on install and update unless a registered migration still reads them (maintainer decision for the storage redesign). Before a change that drops data store users have, list exactly what they lose and get the maintainer's explicit yes. Cleanup on update has no automated test, but it can be checked by hand: copy the build, seed unknown keys in a persistent profile, bump `version` in the copy's `manifest.json`, and relaunch the same profile (`extension-exploratory-qa`).
